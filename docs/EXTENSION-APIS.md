# Extension APIs: probe results

Measured with the API probe (`app/desktop/tests/extensions/api-probe`, run on demand by `SIGNET_E2E_PROBE=1 npm run test:e2e -- extension-api.spec.ts`) on macOS arm64, Electron 45.1.0, on 2026-11-02, on the full stack of branches (safety net, subframes, permissions, small API gaps, lifecycle). The probe loads an MV3 extension requesting every permission of `src/shared/extension-api-catalog.ts` and runs in four contexts: service worker, popup page, options page, and an extension page inside an iframe of the options page.

Status of this document: the results below were measured by that run. The full member by member matrix (152 namespace entries in each context, with every call result) is generated in `app/desktop/test-results/extension-api-probe.md` by the spec and is not reproduced here. Main results confirmed: no probe errors in any context; `browser === chrome` and a frozen `chrome` in all four contexts, the iframe included; the four contexts report the same members; `storage.managed.get` resolves `{}`; `system.storage.getInfo` resolves `[]` without crashing the process; the safety net logs its `stubbed:` and `repaired events:` lines. One open item: the seven `webRequest` events listed under "Gaps" fail `addListener` in the probe. What the probe cannot see (dialogs, shortcuts firing, notification buttons, behaviour across unload and uninstall) is marked **not measured** where it comes up.

- Subframes: **fixed and measured**. - `chrome.clipboard` exists in every context (ChromeOS API, in the catalog as unsupported), like the other unsupported namespaces of the catalog (`audio`, `debugger`, `gcm`, `systemLog`, ...), which are present as objects.

## Namespaces: measured by calls

Provided and answering (same result in all four contexts): `runtime`, `storage` (local, session, sync, managed), `idle`, `alarms`, `permissions` (`getAll` lists the permissions of the manifest, `contains` of an optional one resolves `false`), `tabs`, `windows`, `management`, `declarativeNetRequest`, `scripting` (`getRegisteredContentScripts` resolves `[]`), `cookies`, `i18n`, `offscreen`, `privacy`, `proxy` (`settings.get` resolves `{"mode":"system"}`), `contextMenus`, `notifications` (level `granted`, `getAll` resolves `{}`), `webNavigation` (`getAllFrames` resolves `[]`), `action`, `power`, `dns`, `commands`, `declarativeContent` (`onPageChanged.getRules` resolves `[]`).

Absent (no member in any context): `devtools` (and its sub-namespaces) and the unsupported `browserAction`, `pageAction` and `mimeHandler`. Every other namespace of the catalog now exists (all the ones listed absent on 2026-10-30 are placeholders, see above).

## Gaps seen on 2026-10-30 and where they stand

1. Absent namespaces: **closed**, only `devtools`, `browserAction`, `pageAction` and `mimeHandler` remain absent (see above).
2. Everything in the iframe context: **closed**, the iframe matches the other contexts.
3. `storage.managed` empty and read-only: **closed** (`get` resolves `{}`). `storage.sync` separate from `local`: **still open**, it is an alias of local.
4. Library events with a failing `hasListener` / `hasListeners`: **closed for the library events**. The report has 0 `ev!` from them; the log lists them under `repaired events:` (`action.onClicked`, `tabs.on*`, `commands.onCommand`, `cookies.onChanged`, `downloads.on*`, `webNavigation.on*`, ...). Seven `webRequest` events (`onBeforeRedirect`, `onBeforeRequest`, `onBeforeSendHeaders`, `onCompleted`, `onErrorOccurred`, `onResponseStarted`, `onSendHeaders`) show `ev!` in all four contexts with `addListener: No matching signature.`: this comes from the probe, not from Signet. The probe calls `addListener(fn)` without the request filter these events require, and Chrome rejects that call with the same error. `onAuthRequired` (Signet's) and `onHeadersReceived` accept it; the worker line `native onAuthRequired.addListener failed` is the same missing filter forwarded to the native event. Passing `{ urls: ['<all_urls>'] }` in the probe would remove these entries.
5. `downloads` stub and `action.isEnabled`: `downloads.search` still resolves `undefined` (stub); `action.isEnabled` now resolves `true`.
6. Optional permissions path: members and basic calls measured (see "chrome.permissions"); the request and dialog flow is **not measured**.

## Surprises

- Reloading an unpacked extension while its worker is running the probe killed the whole Electron process in several runs. The unpacked mechanism watches the folder, and on macOS the file watcher replayed the files just copied, triggering a reload about 400 ms after loading. The spec therefore loads the probe with `session.extensions.loadExtension` directly. This is worth a separate look: a developer saving a file in a busy extension could crash Signet.
- The two sandboxed popup/options pages in tabs report no errors and run Signet's preload, as expected.
- Keys outside the catalog: none on `chrome` or `browser` in any context in the 2026-11-02 run (`clipboard` is now in the catalog).

## Safety net (implemented after this probe)

Status: implemented, unit-tested and measured by the probe on 2026-11-02 for what a probe can see (below).

- **Placeholders**: for every namespace of the catalog the extension may use (permission, optional permission or manifest key), missing methods report `chrome.<ns>.<member> is not supported in Signet` (`runtime.lastError` or rejection), `soft` methods resolve a neutral value, missing events accept listeners and never fire, and constants, enums and classes exist. Existing members are never replaced, except the two cases below. The list of placeholders is logged once per extension version in development (`[extension-apis] <id> stubbed: ...`). Measured: the `stubbed:` log line lists them (including whole namespaces such as `bookmarks`, `history`, `userScripts`, `tabGroups`, `sidePanel`), the placeholder calls above reject or resolve as described, and placeholder events report `ev` in every context.
- **Library events**: events whose `hasListener`/`hasListeners` threw "Method not implemented" get listener tracking (`fixedEvents` in the install report). Measured: the `repaired events:` log line lists them, and no repaired event is `ev!`. The seven `webRequest` entries still marked `ev!` come from the probe calling `addListener` without a filter (see the gaps), not from a broken event.
- **Native crashers** (catalog field `crashes`): `system.storage` (`ejectDevice`, `getAvailableCapacity`, `getInfo`, `onAttached`, `onDetached`) and the four `printerProvider` events are replaced by inert placeholders, because the probe saw the whole process die when listeners were added to them. `system.cpu`, `system.memory` and `system.display` stay native: their `getInfo` calls resolved when explicitly enabled. The probe no longer skips any of these by default, and this run completed without a crash: `system.storage.getInfo` resolves `[]`, and the `system.storage` and `printerProvider` events accept listeners.
- **storage.managed** is an empty read-only area in every context (measured: `get` resolves `{}`). `storage.sync` is unchanged (still an alias of local, measured).
- **Subframes**: the preload and the call router accept any `chrome-extension://` frame (not only the top frame), except sandboxed pages (opaque origin). Electron only runs frame preloads in subframes when the webContents has `nodeIntegrationInSubFrames: true` (it does not enable Node), so tabs and offscreen documents now set it; before that, the preload never ran in iframes. **Measured**: the iframe context now gets Signet's APIs, `browser === chrome`, no error and no crash.
- **Unpacked extensions**: reloads are now conditional on a real file change, serialised and preceded by a clean unload (see SPEC.md). The probe still loads its extension directly.

## chrome.permissions (implemented after the safety net)

Status: implemented and unit-tested; the probe now confirms the members and the harmless calls only. In all four contexts `request`, `contains`, `getAll`, `remove`, `onAdded`, `onRemoved`, `addHostAccessRequest` and `removeHostAccessRequest` exist (the last two are placeholders), `getAll` resolves the permissions of the manifest and `contains` of an optional permission resolves `false`. **Not measured**: the request dialog, the stored grants, `onAdded` / `onRemoved` firing, `remove` and the effect on the call router.

Signet replaces the whole `permissions` namespace (`request`, `contains`, `getAll`, `remove`, `onAdded`, `onRemoved`) in every extension context; the library's in-memory implementation, which auto-granted everything and never fired events, is no longer used. `addHostAccessRequest` and `removeHostAccessRequest` stay placeholders. Code: `apis/permissions.ts`.

- **Store**: optional grants given at runtime are kept in `<userData>/extension-permissions.json` as `{ [extensionId]: { permissions, origins } }` (atomic, debounced write). The effective permissions of an extension are `permissions` + `host_permissions` of the manifest plus its grants.
- **request**: each permission must be in `permissions` or `optional_permissions`, each origin must be covered by a pattern of `host_permissions` or `optional_host_permissions`; otherwise it rejects with "Only permissions specified in the manifest may be requested." If everything is held already it resolves `true` without a dialog. Otherwise one native dialog lists only the new items (Allow / Deny). Allow stores the grant, fires `permissions.onAdded` in every context of the extension in every session and resolves `true`; Deny resolves `false`. Requests of one extension are served one after the other, and each one asks only for what is still missing. A request containing only low-risk permissions (the quiet list of the install dialog, such as `storage`) is granted without a dialog. Signet does not require a user gesture.
- **contains / getAll**: use the effective set; an origin counts when a held pattern covers it.
- **remove**: rejects with "You cannot remove required permissions." for manifest permissions and hosts; optional grants are deleted (`onRemoved` fires) and it resolves `true`. Removing something not held resolves `true` (not confirmed against Chrome). Only the exact granted pattern can be removed, not a part of a broader one.
- **Applied everywhere**: the call router (so an optional permission gives access once granted, without a reload; before that the call fails with "the '<name>' permission is required") and the lookup of extensions holding a permission use the effective permissions. The namespaces of optional permissions are installed from the start, so feature detection keeps working. The `declarativeNetRequest` engine now counts `optional_host_permissions` only once granted (before, they counted as granted because there was no prompt) and recomputes when grants change.
- **Lifecycle**: grants are kept across an unload (reload of an unpacked extension, store update) and dropped only on uninstall (see "Unload versus uninstall"). Items the manifest no longer lists as optional are dropped when it loads.
- **Not honoured**: an optional `nativeMessaging` permission granted at runtime. The library checks `manifest.permissions` itself for `runtime.connectNative` and `sendNativeMessage`, so honouring the grant would need patching the library or proxying native ports; extensions that link to a desktop app must declare it as required.

## Unload versus uninstall

Status: implemented and unit-tested (`apis/lifecycle.ts`); **not measured**, because the probe never unloads, reloads or uninstalls its extension (it only shows that the alarm, permission and context menu members exist and answer). An unload happens on reload of an unpacked extension and on store updates; Chrome keeps the extension's data through both. Signet used to wipe it on every unload.

| store                                                                         | on unload (runtime only)                                                                                                                                                                               | on uninstall (`forgetExtension`) |
| ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------- |
| permission grants                                                             | kept (reconciled against the manifest when it loads)                                                                                                                                                   | dropped                          |
| saved context menu items                                                      | kept                                                                                                                                                                                                   | dropped, on disk too             |
| declarativeNetRequest                                                         | dynamic rules, enabled rulesets and the action count setting kept; session rules (memory only) cleared                                                                                                 | all dropped                      |
| controlled settings (proxy, privacy)                                          | kept; the proxy of that session goes back to the system until the extension loads again                                                                                                                | released                         |
| alarms                                                                        | kept, timers stopped then armed again on load (Chrome documents that alarms may be cleared on update, but Signet cannot tell an update from a reload and `onInstalled` may not fire, so it keeps them) | dropped                          |
| commands, notifications, offscreen documents, injected CSS keys, button state | released                                                                                                                                                                                               | released                         |

`chrome.storage` belongs to Electron and is left alone. Uninstall paths: the confirmed removal in `extensions.ts` and the removal of an unpacked extension (`unpacked.ts`, not its reload). At startup, once store and unpacked extensions are loaded, `collectGarbage` drops stored data of ids that are no longer installed (folder deleted by hand). It is skipped if a session failed to load its extensions or an unpacked extension could not be loaded, since a missing id then proves nothing.
